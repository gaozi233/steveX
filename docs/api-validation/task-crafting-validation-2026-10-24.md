# 新任务循环的复杂合成实测

2026-10-24。真实 Minecraft Java 1.21.11，DeepSeek deepseek-v4-flash，Task-A 生存模式，旁边预置工作台。通过生产 HTTP planner/message 的 continuous 模式运行，没有脚本逐步驱动 tick，没有自动配方选择、递归规划或合成专用记忆。

## 条件与判据

- 初始材料和任务文本复用 scripts/craft-llm-acceptance.js 的历史场景。旧测试只开放 inventory／recipes／craft／say，本轮使用当前完整默认目录，不能作为严格改进前后对照。
- 每项最多36次调用、240秒；首批总上限140次，因此批量铁器剩余31次预算。后两项另立限额测试，不放宽已失败场景的预算。
- 模型自己查询和执行。验收脚本只准备场景、记录结果和独立评分；观察到已执行的 say DONE／BLOCKED 后外部暂停，不把它写成 Brain 自动完成能力。
- 物品达成要求客户端背包和服务端无损计数都恰好满足目标；结束判据要求对应 DONE／BLOCKED。缺料任务还检查初始材料保留。二者分别统计，不能混为成功。
- 连续循环可能在外部验收器读到 DONE 前已发出下一次请求，随暂停取消；该调用照常计入，不假设供应商停止计费。

## 发现与处理

目前前五项未观察到 craft 执行失败或命令格式拒绝；不能把模型查询低效或预算耗尽改记为 API 故障。混合木材与批量铁器已达到物品目标但继续查背包，说明调度循环不等于可靠的目标核验与停止策略。红石任务还存在长链中的遗漏与重复查询。

本轮不添加针对目标物品的完成规则，不自动补材料、不代替模型计算依赖、不临时扩张失败场景预算。一般上下文管理与通用任务结束协议仍是后续架构议题；这些失败记录保留，不用重跑成功覆盖。

新增 scripts/task-crafting-live.js，直接走真实任务接口；补充评分回归，防止“只说DONE”“客户端与服务端不一致”“多产出”或“缺料时消耗原料”被算作成功。原始提示词、过程结果与供应商usage仅保存在忽略的 runs/task-runtime，不入Git。测试不修改固定system。

本轮未发现需修改生产craft／recipes或任务调度执行逻辑的故障，未为追求通过率修改这些接口。修正的是验收评分：不把物品齐全直接算成任务结束；缺料与保留材料同时核对服务端。新增4项评分回归。测试夹具和材料已清理，Task-A恢复原位置／模式，Task-B未参与合成；真实服务保留，当前无运行中任务。未提交推送。

最终全库自动回归490/490通过。该数字是代码回归，不替代上表严格5/8的真实任务结果。
