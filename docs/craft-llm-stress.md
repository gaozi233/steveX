# DeepSeek 复杂合成与长程分解压力验收

## 方法与边界

这是生产 Brain、命令 API 与真实 Minecraft 生存玩家的集成验收，不是 Minecraft 开放世界自主能力基准。只开放 inventory、recipes、craft、say；固定提供可触及工作台，不允许采集、创造物品或外部补给。通过真实 DeepSeek API 决策，不给出中间合成步骤。初始物品由测试夹具发放，模型只能从正常状态查询读取，不接收 RCON 真值或评测器计划。

保持生产 Brain 最近 10 条完整结果的历史策略，不为通过测试增加外部规划器、配方搜索器或额外记忆。每步保存完整提示词、模型回复、实际命令、服务器确认结果、耗时和输入字符数。字符数不是 token 数，也不是费用。达到 10 条历史只说明开始发生记录淘汰，不自动证明模型遗忘了必要信息。

每例新建 Brain 并重置测试背包，各场景之间不共享历史。自动测试中另有原生配方的可行路线，只验证测试材料确实足够，不提供给运行中的模型，也不替模型选配方。记录的是可见命令与执行效果，不是模型内部思维链。

每例最多 36 次模型调用、4 分钟；整轮最多 140 次调用、15 分钟。限额在步骤边界检查，模型请求还受剩余时限约束；在途游戏动作及清理可能额外占用时间。不把超限、模型错误或不完整场景计为通过。达到限额不会自动扩预算或无限重试。

所有正常场景按最终背包同时存在的目标数量验收，不把曾经合成过、后来消耗掉的物品算成最终成功。材料不足场景单独判断正确拒绝；不能将其称为“成功合成铁砧”。最终均通过服务端 Inventory 和 clear <item> 0 无损计数独立核对，不以 say DONE 为唯一证据。查询覆盖与任务结果分别保留在 assessment 中。

## 复测命令

```powershell
# 只看设计，不调用模型或游戏
node scripts/craft-llm-acceptance.js --stress

# 全部压力场景，复用 DPAPI Key
./scripts/query-llm-acceptance.ps1 -Suite craft-stress

# 只复测一个场景
./scripts/query-llm-acceptance.ps1 -Suite craft-stress -Case redstone-tight-budget

# 进一步缩小调用预算，只能降低，不能突破套件上限
./scripts/query-llm-acceptance.ps1 -Suite craft-stress -Case powered-rail-384 -MaxModelCalls 20
```

需要已启动的本地 8090 SteveX 验收服务、25565 Minecraft 测试服务器和本机 RCON 夹具；玩家 SteveX-Test 须为空背包、无装备、生存模式。不会清除人工玩家背包或移动人工玩家。结束清理临时物品／工作台，恢复测试玩家原位置及朝向。原始日志保存在 runs/craft-llm 忽略目录，Key 不写入报告。

## 发现与修复

### 批量合成撞上通用动作时限

首轮 `craft powered_rail 64 table` 在约 30.1 秒被通用动作时限取消。最终服务端实际有 258 根；completedExecutions=42 只表示完整经过逐次确认的次数，不意味着恰好只发生 42 次合成。取消发生在点击与确认之间，实际已有 43 次产物，所以不能直接按 requested-completed 补做。

模型通过 inventory 读取实际 258 根，再补做 21 次得到剩余 126 根，最终 384。这是修复前的真实失败恢复证据，不是修复后已无风险的证明。

修复内容：

- `src/commands/craft_timing.js`：合法 1..64 次合成的默认动作时限为 `30000 + (times - 1) * 1000` 毫秒，即 30..93 秒；非法次数仍走参数拒绝，不获得更长时限。
- `src/agent/agent.js`：只对 craft 应用该默认值；调用者明确 timeoutMs、runtime.actionTimeoutMs 仍优先，其他动作不变。停止／取消和部分效果核对保留，不关闭看门狗。
- `scripts/craft-llm-acceptance.js`：相应延长合成 HTTP 等待，避免客户端先超时并丢失仍在进行的操作结果。
- `src/agent/brain.js`：失败历史保留不同于 error 的 output，以及 completedExecutions、producedCount、changes；不只记一个 timed out，避免丢失部分产出。新反馈传入历史由自动测试覆盖；上述真实恢复发生于这项修复之前。
- craft 目录描述补回次数 1..64，网页、文档、LLM 提示词同步生成。

修复后重启服务，用 DeepSeek 从同样初始材料重新执行动力铁轨路线：13 次调用，103.1 秒，全部通过；关键单次 `craft powered_rail 64 table` 约 45.3 秒完成，completedExecutions=64、producedCount=384，服务端无损计数确认 384，无合成失败。日志：`runs/craft-llm/1792685405844.json`。这验证了正常本机条件下的大批量，不保证低 TPS／掉线永不超时。

### 验收器误拒带说明的结束命令

缺料场景中，模型已经正确指出铁砧需 31 铁锭当量，而现有 3 铁块只有 27，并输出 `say BLOCKED` 加说明。这符合生产 say 接口，但旧验收器只允许精确的 `say BLOCKED`，误拒了 6 条解释并继续付费调用。

现允许 DONE／BLOCKED 后附单行说明，仍禁止非白名单动作与多行命令；新增 rejectedCommands 记录，区分生产 Brain 解析拒绝和测试白名单拒绝，不将测试器的限制错归为模型错误。旧 6 条原始响应离线重放 6/6 接受；专项 DeepSeek 复测 3 次调用后正确 BLOCKED，服务端确认无铁砧且原料未消耗，日志：`runs/craft-llm/1792685553771.json`。该专项恰好输出简短 BLOCKED，带说明的识别由原始响应重放和自动测试另行验证。

两次专项额外调用 13+3，本轮总计 **136 次**，未超过最初 140 次预算。没有自动追加预算或无限重试。

## 结论与未覆盖

六条复杂路线的材料拆解、候选配方选择、共享资源分配和多目标合成均有真实通过证据；最大单例 32 次决策。最长输入为 14,696 个 JavaScript 字符，不是 token 数；六个可行场景均达到 10 条历史窗口。红石场景重复查询 10 次，值得在后续上下文管理中减少重复读取，但单轮记录不足以断定重复全由历史淘汰导致。

本轮没有为具体任务新增递归合成器、预写行为树、规划脚本或模型专属步骤。修复的是批量动作时限和反馈，以及验收器公平性，不是硬编码任务答案。

当前自动回归 **176/176** 通过，覆盖材料可行性、多目标同时达标、正确拒绝、时限边界／显式配置优先、部分产出历史和结束说明识别。原始日志与 DPAPI Key 均在 runs 忽略目录，未提交或推送。临时物品、工作台已清理，测试玩家恢复原坐标朝向，服务继续运行。

尚未覆盖：真实采集／烧炼／容器取材、空间移动、多人干扰、模组或动态配方、低 TPS／断线、极满背包的复杂返还物、不同随机种子和多次重复统计。因此这是有界串行长程规划压力验收，不是多 Agent 并发压测，也不能证明通用任务能力或最优资源利用。
